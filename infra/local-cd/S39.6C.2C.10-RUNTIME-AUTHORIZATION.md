## Approval and runtime loading

New maintenance/authorization.ts separates two Ed25519 roles:

- independent reviewer signs a ReviewedApproval, binding source/build/graph and
  compiled artifact digests, expected effect-path universe, individual reviewed
  paths, immutable image ID and intended project/service;
- trusted Docker controller signs a short-lived HostAttestation after obtaining
  independent daemon metadata. Its public key must differ from the reviewer's
  key by actual DER identity, not merely PEM formatting.

Canonical signatures use deterministic code-point key order. Public-key-only
SPKI inputs are accepted; private-key PEM cannot be provisioned as a trust key.
Keys carried in requests or ordinary environment variables are never accepted.

The supported authorization audience is deliberately limited to
S396_SYNTHETIC_HTTP_V1, project narration-s396-c10, service backend. This is not a
general production rollout switch or approval for another environment.

authorization-loader.ts is invoked during normal startup and fails closed when
the following externally provisioned artifacts are absent/invalid:

| Fixed path | Purpose |
| --- | --- |
| /run/s396-fencing/trust.json | Public reviewer/controller keys, provisioned by trusted host |
| /run/s396-fencing/approval.json | Signed independent ReviewedApproval |
| /app/fencing-build.json | Build identity, expected path set and compiled JS artifact manifest |

Linux non-root runtime is required. Trust directory/files and build manifest
must be root-owned, non-symlink, not writable by group/other; public files are
readable by Node but not writable by that unprivileged process. The trusted root/
Docker host remains outside this application threat boundary. A deployment must
provision these as approved read-only artifacts; no mounting/provisioning was
performed here. No private signing key belongs in the Backend.

The loader hashes the complete actual /app/dist JS tree, rejects symlinked
artifacts, and compares its digest with the manifest and signed approval. Build,
source and graph identity must agree. Expected path set must match exactly,
without duplicates, missing paths, UNKNOWN classifications or absent registration/
completion/test evidence. Digests must be SHA-256-shaped; expired approvals fail.

The signed expected universe comes from the independent review/build process,
not a Backend claim that zero counters prove coverage. Cryptography authenticates
that approval; it cannot establish that an incomplete audit was correct. The
reviewer must first certify the complete reachable-effect scope, including
callbacks/resources, rather than simply sign the C.8 caller-only snapshot.

## Atomic runtime authorization flow

1. Existing authenticated loopback control checks the loaded authority. Without
   it, /maintenance/fence still returns FENCING_COVERAGE_UNPROVEN.
2. Signed host assertion binds profile digest, deployment operation owner, nonce,
   full container/image, Compose project/service, process boot/deployment identity,
   drain operation, activity revision and the NEXT fence generation.
3. Assertion lifetime is at most 10 seconds and never beyond approval expiry.
   Nonces are process-local one-use; a bounded replay registry fails closed at
   capacity. First valid assertion pins the deployment owner for that drain;
   a competing owner is rejected even with a different nonce.
4. Control obtains a bounded database observation, then verifies the signature
   and live process binding. Missing/failed DB observation does not grant a fence.
5. Verifier creates an opaque grant in a private WeakMap. Neither a JSON object,
   boolean flag, unsigned certificate nor self-declared profile can forge it.
6. Coordinator rechecks quiescence/coverage/revision and consumes the grant in
   the same synchronous turn as terminal registration closure. Activity after
   attestation invalidates the grant; new work cannot enter after FENCED.
7. Fence token includes approved profile/image/project/service and deployment
   operation, in addition to boot/drain/container/revision/generation/expiry.
   Expiry does not reopen admission. Owner replay and process restart fail closed.

Old SYNTHETIC_CLOSED_WORLD fixtures remain test support; the normal singleton is
UNPROVEN unless this verified-grant route succeeds. No hardcoded coverage=true or
environment bypass was added to the normal authorization path.

## Identity and shutdown binding

The existing C.8 check-only observer is NOT promoted into a signing authority.
A future trusted controller must independently inspect exact container ID,
immutable image ID, Compose identity, StartedAt/mount/command and process boot,
then sign with its externally held controller key. If Docker metadata cannot be
read or changes, it must not issue an assertion. That real issuer/provisioning
step remains unimplemented/unapproved; the verifier does not query Docker itself
or accept request/env container claims as independent truth.

After a valid grant, the coordinator stores verified container/profile binding.
Only that binding lets the loaded authority resolve the container identity for
existing one-time shutdown authorization. Wrong token/owner/generation/boot still
fails exact live validation. No shutdown was invoked in this task. The production
Backend images currently running contain none of this new source yet.

## Safety gate

upgrade/rollback scripts. It is a separate check-only consumer, not a replacement
action or a bypass of the old replacement gate.

It checks independent Docker ID/image/StartedAt/project/service before and after,
expected deployment owner/profile digest, bound token image/container/generation/
expiry, and authenticated same-process /maintenance/verify-fence. A valid result
still has replacementAllowed=false. It never substitutes a drain certificate.
Connection/identity/profile failures throw. Old Backend upgrade/rollback guards
remain blocked. No check-and-stop flow or new deployment capability was added.
