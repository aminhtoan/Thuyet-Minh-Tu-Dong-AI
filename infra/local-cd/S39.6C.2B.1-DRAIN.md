All unexpired RAM drafts are conservatively counted as unrecoverableLiveDrafts,
even where a Customer draft may also have durable recovery. This can overblock;
it never treats an unverified durable copy as proof a draft can be discarded.
Store timeout timers may remain until normal expiry; no automatic draft clearing.
No persistent scheduler/worker was introduced. CLI/seeding scripts are not normal
HTTP admission paths and must not run concurrently during future maintenance.

## Internal control channel

Disabled unless MAINTENANCE_CONTROL_ENABLED=true. Optional names only; no env
file or live secret is modified:

- MAINTENANCE_CONTROL_TOKEN: required when enabled, at least 32 bytes.
- MAINTENANCE_CONTROL_PORT: default 9091, must differ from public PORT.

Separate HTTP server binds 127.0.0.1 in the Backend container namespace. It is
not registered in /api and no Docker port is published. Future operator tooling
must reach that loopback in the SAME container, not start another Backend process
to infer RAM. HOSTNAME is observational deployment identity, not cryptographic
proof; future tooling must bind it to docker inspect image/container ID.

Authenticated routes:

- POST /maintenance/close: idempotently closes admission and generates operation ID.
- GET /maintenance/status: process/RAM counters and read-only database observation.
- POST /maintenance/open: reopens admission, invalidating operation ID.

Bearer token is checked in constant time after length validation. Loopback-only
peer check, 20 authorized requests/10s, one status DB observation at a time,
bounded DB command time and fixed error summaries. No CORS control access is
added. No token/request-body/payload/transcript is logged or returned.
Future Nginx config explicitly rejects /maintenance and /api/maintenance.
Current static images are NOT rebuilt; the separate control port is not proxied
by their existing /api upstream either. Offline HTTP tests verify normal API
router has no control endpoint. No live Docker control-channel test was run.

## Drain observation versus certificate

Same-process snapshot contains bootId, drainOperationId, admissionClosed,
activeBusinessRequests, activeOperations, providerCalls, pendingApprovals,
unrecoverableLiveDrafts, pendingStoreOperations and observerKnown. Database
summary includes connected, activeJobs and unresolved CLAIMED/UNCERTAIN attempts.
Read failure/timeout gives UNKNOWN. Counts are observations, not an atomic DB/RAM
snapshot across all writers. Source is designed for one Backend process only.

This foundation intentionally returns status BLOCKED, coverageComplete=false,
certificate=null even when known counts are zero. Detached audit writes and
alternate entry points are not fully instrumented yet. No automatic override,
manual confirmation flag or fabricated PASS certificate exists. Boot ID/operation
ID/deployment identity are present for future certificate binding, but cannot
authorize replacement in this step. Existing upgrade/rollback guards remain.
