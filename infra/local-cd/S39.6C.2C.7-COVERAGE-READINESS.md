## Container identity attestation design

Independent trust source: trusted Windows controller querying the local Docker
daemon, with immutable release image ID and exact full container ID pinned in a
manifest. The Backend request/environment is not that independent source.

Proposed handshake (NOT implemented as production authorization):

1. Controller holds exclusive project deployment lock and pins expected image,
   full container ID, StartedAt and Compose project from release/daemon records.
   Inspect actual mounts/command to ensure this is the approved normal-server
   artifact, not merely a matching tag or arbitrary mounted script.
2. Controller creates a fresh random challenge and reads current process boot,
   deployment identity, FENCED state, admission and generation through a scoped
   client in that exact container's namespace. The client only reads the actual
   control process; it never infers RAM from a second Node process.
3. Inspect again; reject changed container/image/StartedAt/project. Bind challenge,
   boot, generation, drain operation/revision, image and full container identity
   in a short-lived, one-use controller-signed attestation. A public verification
   key pinned by the approved image/read-only configuration identifies the host
   controller; container self-claims or unsigned request/env cannot substitute.
4. Backend verifies signature, audience, freshness and live fence identity before
   authorization; controller revalidates live identity immediately before any
   future operation. Terminal fence, not repeated verification, prevents work.
   Current task performs no replacement and implements no signing authority.

New staging/identity-attestation.mjs validates offline fixtures of independent
Docker-before/after observations against live process claims. It rejects wrong
container/image/StartedAt/project, challenge, boot, generation/deployment and
open admission. Even matching input yields IDENTITY_MATCHED_CHECK_ONLY with
replacementAllowed=false. It does NOT authenticate the origin of arbitrary
JSON passed to it, verify a signature, install a trusted key, query live boot ID,
or issue a token. Unit input validation is not deployed attestation.

Current createDrainControl still receives no attested container identity from
server.ts, so /maintenance/authorize-shutdown remains blocked. No fake identity
was supplied to enable production shutdown. An out-of-band Docker administrator
can kill/replace a container regardless of application fencing; the trust model
must constrain such actors and all competing deployment controllers.
