## FENCED shutdown protocol

1. A process must already be FENCED. authorizeShutdown requires the exact live
   token, matching boot/drain/deployment/container/generation/revision/expiry,
   and consumes it once. Authorization does not mean shutdown is safe/completed.
2. Authenticated loopback POST /maintenance/authorize-shutdown accepts the token
   only when the control server has an attested container identity supplied by
   its trusted bootstrap. Current normal server supplies NO such attestation:
   endpoint returns 409 CONTAINER_IDENTITY_UNATTESTED. Request body cannot assert
   its own trusted identity. No production authorization was enabled.
3. SIGTERM/SIGINT in FENCED cannot authorize itself or reopen admission. The
   server delegates to shutdownFenced, which requires prior authorization.
   Repeated signals share the same in-flight promise rather than announcing an
   early success. Ordinary non-FENCED shutdown remains on its original path.
4. Fixed server-owned internal cleanup closes HTTP, closes private control, then
   calls mongoose.disconnect directly. It is intentionally NOT a new business
   operation (which FENCED rejects). No draft deletion, job retry, provider call,
   schema operation or process.exit is added. The cleanup callback is not taken
   from a request or serialized token.
5. States: NONE -> AUTHORIZED -> CLEANING -> SAFE or FAILED. A 5s default bound
   covers cleanup. Timeout does not cancel work or allow another attempt; late
   completion after timeout cannot turn FAILED into SAFE. Admission remains
   closed throughout, including failed/expired/aborted operations.
6. Shutdown errors set process.exitCode=1; only successful completion sets 0.
   The previous unconditional finally exitCode=0 was removed. No process.exit
   is used to hide failure. SAFE is only process-local cleanup evidence, not a
   durable receipt of container termination; no runtime attestation is claimed.

Authorization pins the already validated owner for this one terminal shutdown;
expiry cannot reopen the process. A crash loses its RAM authorization and boot
identity; an old token is invalid in a new process. No automatic unfreeze exists.

### Docker timeout/SIGKILL boundary

Docker may send SIGKILL after its own stop deadline. SIGKILL cannot be handled,
await cleanup or publish a safe receipt. A stopped container alone is never proof
of safe cleanup. Future consumer must require a durable owner-bound cleanup
receipt and distinguish graceful completion, timeout, OOM and kill. Docker stop
budget must exceed the internal cleanup budget with margin; no such Docker
behavior was configured/tested in this task. Cleanup timeout here is fail-closed,
not a guarantee the OS/driver has physically stopped.
