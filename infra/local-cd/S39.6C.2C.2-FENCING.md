## State machine and atomicity

RUNNING -> close() -> MAINTENANCE -> startDraining() -> DRAINING.
establishFence() may synchronously commit FENCED only in an explicitly synthetic
closed-world runtime, after normal coverage, all counters, RAM observers and DB
zero/connected observation with unchanged activity revision pass. No await exists
between the final check and terminal transition. Registration and transition
serialize on the same JS event loop. Registration first prevents fencing;
fencing first rejects registration before track() executes the supplied action.
This is not a claim of distributed atomicity or database ownership fencing.

FENCED rejects begin(), enterRequest(), track(), new observers/entry points and
open(). Repeated close does not reopen it. There is deliberately no unfreeze API.
Token expiry, deploy abort, control disconnection and token consumption cannot
change admission. Existing work is not cancelled or retried. Live RAM drafts and
approvals prevent fencing rather than being discarded.

## Tokens

Synthetic tokens contain a random opaque secret, boot ID, drain operation ID,
deployment/container identity, activity revision, monotonic in-process generation
and 10-second expiration. The issuing process compares the exact stored token,
checks current state/coverage/counters/expiry and allows consumption once only.
A new process has no matching token, boot ID or stored authorization. Token data
and secrets are not added to snapshots or logs. These are process-local bearer
tokens, not signed cross-process attestations or proof of Docker identity.

## Protected paths and observed gaps

Existing request/provider/approval/detached operation tracking now refuses new
registration in FENCED. Multer registers before callbacks. Read-stream creation
and FFmpeg spawn now use createTrackedResource(): registration BEFORE creation,
release on close or synchronous creation error, preserving prior lifetimes.

However normal HTTP coverage is not closed-world side-effect coverage. Direct
service imports can execute model writes without a registration at service entry;
other media/TTS child creation and all arbitrary background callbacks have not
been proven pre-registered. A counter around an admitted HTTP promise alone
does not establish an exclusive capability for every side effect. Shared DB
writers and actual container-identity attestation remain unresolved. Health route
behavior in a truly fenced normal-server profile also needs runtime acceptance.

Therefore the production singleton is always UNPROVEN. NORMAL_HTTP_V1 is NOT
promoted into fencing permission. SYNTHETIC_CLOSED_WORLD is constructor-only test
setup, never enabled through configuration, control requests or environment.
Authenticated loopback POST /maintenance/fence returns 409
FENCING_COVERAGE_UNPROVEN, never a token. It moves closed maintenance to DRAINING
only. Production can still perform its previous nonterminal maintenance/open
flow; no production process can reach FENCED through the current control API.

## Safety gate integration

Test-BackendReplacementGate.ps1 now requires -RequireFence in the existing
consumer. It preserves container/image/StartedAt verification, certificate
validation, the shared exclusive lock and durable journal. Without an attested
fenced-token protocol it throws FENCING_COVERAGE_UNPROVEN. No certificate alone
can grant replacement, no fallback bypass and no destructive callback exists.
It is intentionally not a completed Docker fencing-token consumer. Existing
backend upgrade/rollback rejection remains unchanged. An attempted gate failure
is journaled FAILED and blocks unattended continuation.
